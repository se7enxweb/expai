# expai 0.0.1.19 (2026-10-24)

Translation services: DeepL and LibreTranslate next to the model, per language pair and purpose.

## Added

- Added: Translation services ([../translation-providers.md](../translation-providers.md)). The translation sync, the
  field action Translate and the chain step translate hand their texts to the service of the language pair and
  purpose (`patch`, `full`, `field`): `[TranslationSettings] Provider=` and `ProviderFor[<source>:<target>:<purpose>]=`,
  each naming a `[TranslationProvider_<id>]` group (`Class=` implementing the new interface `expAiTranslationProvider`).
  The default is `llm`, the model providers of expai, with the request of earlier versions byte for byte (a snapshot
  test keeps it so); an installation without the group behaves as before.
- Added: Two machine translation services: DeepL (`expAiTranslationProviderDeepl`: XML tag handling for the
  placeholders, terms that are never translated, glossary id, formality, context, billed characters) and LibreTranslate
  (`expAiTranslationProviderLibreTranslate`, usually local, `Region=local`). Both are inactive until a rule names them;
  DeepL needs a key in settings/override.
- Added: `[TranslationSettings] Fallback=llm`: used only when the chosen service is not configured, does not translate
  the pair or the data policy keeps the content away from it. A failure while translating never falls back.
- Added: The job type `expai.translation.run` (`expAiTranslationRunHandler`) for translations by a machine translation
  service: master switch, budget reservation and hold, the data policy and a conflicting edit checked again, the answer
  in the checkpoint, the draft written by the applier of the translation sync. Model translations stay `expai.request`
  jobs with their lanes.
- Added: The states `no_provider` and `blocked` of the translation sync, with the reason; nothing is queued, Approve
  refuses, the Translations section says so and shows "Translated by <service>" instead of a lane. The CLI takes
  `--provider=<id>`, names the service per line and exits with 2 when a translation has no service.
- Added: `expAiTranslationRecorder`: the usage row of a translation service (provider = its id, `model_alias`
  `translation.<id>`, `reported_cost_micros`, the new column `billed_chars`), the gate and the cost limits before the
  request, the audit event as for a model.
- Added: EI: Summary lists the translation services, the rules, the fallback, the key source of each service and why
  it cannot be used; the extension point survey has the registry `expai_translation_providers`.
- Added: The UI strings of translation services in every shipped catalogue.

## Updated

- Updated: `expai_usage_log` has the column `billed_chars`. Run `php extension/expai/bin/php/expaischema.php
  --install -s <siteaccess>`; until then the characters are not stored (one warning per process), the cost is.
- Updated: `[FieldAction_translate] Handler=expAiTranslateFieldAction` (with `llm` the same prompt as before). The edit
  form leaves Translate out when no service can translate fields (`fetch( 'expai', 'unavailable_field_actions' )`).
- Updated: The chain step translate is skipped with the reason when no translation service can take any of its
  languages.
- Updated: `expAiProviderRegistry::keyPlacementProblems()` also checks the keys of `[SearchProvider_<id>]` and
  `[TranslationProvider_<id>]`; an `ApiKey` of the web search service in a tracked file was not reported before.
- Updated: `expAiLimits::check()` takes `units` (a translation service is checked against the cost limits only), and a
  usage row with the model alias `translation.<id>` is priced with the cost it stored.
